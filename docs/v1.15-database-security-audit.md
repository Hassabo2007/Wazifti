# V1.15 database security and migration hygiene

## Scope
This branch contains a narrowly scoped, additive database migration. It is intentionally not applied to production.

## Changes proposed
- Add five indexes for foreign keys flagged by Supabase Performance Advisor: in_app_notifications(application_id), job_messages(application_id), job_messages(candidate_id), job_messages(poster_id), job_messages(sender_id).
- Rewrite the two job_messages SELECT/INSERT policies to wrap auth.uid() in scalar SELECTs, preserving participant and ownership checks while avoiding per-row auth function evaluation.

## Findings deliberately not changed
- public.admin_users and public.push_notification_events have RLS enabled with no policies. This denies direct client access and is intentional; do not add permissive policies.
- is_admin, finalize_job_hiring, update_individual_job_application_status, and update_owned_company_description are SECURITY DEFINER functions. Current grants deny anon and PUBLIC; authenticated execution is required by current app flows. Their identity/ownership checks and empty search_path settings are retained.
- Leaked-password protection is an Auth dashboard/plan capability. It cannot be enabled by a SQL migration; enable it in Supabase Auth settings if the current plan exposes it.
- pg_net is installed in public, but scheduled alert routines use net.*. Moving it without coordinated scheduler changes risks breaking notifications; defer to a dedicated tested change.

## Migration history drift — unresolved
Production migration ledger currently contains 26 applied entries, while main currently tracks 20 SQL migration files. Several ledger names do not match tracked filenames, including historical changes for application guards, taxonomy/experience, employer policies, push subscriptions, in-app notifications, individual job posting, and later messaging policy hardening.

Do not mark historical migrations as applied or invent replacement SQL. Reconcile by recovering exact historical SQL from Git history/PRs or producing a verified schema baseline and documenting which tracked migrations it represents. Until then, do not use a clean-database replay as a production parity test.

## Validation required before merge
1. Apply this migration to an isolated Supabase development branch.
2. Re-run Security and Performance Advisors.
3. Verify message read/send for candidate and employer/individual poster, plus denial for a non-participant.
4. Verify admin dashboard, job hiring finalization, and company-description update flows.
5. Compare migration ledger against repository and close drift separately.
6. Run site smoke tests before merging.

## Production safety
No production schema, data, Auth setting, or deployment was changed by this branch.
