# نظام تنبيهات الوظائف — تصميم معتمد ومراجعة التنفيذ

**الحالة:** التصميم معتمد من صاحب المشروع. ملف SQL الموجود في `docs/sql/job-alerts-system-draft.sql` مسودة للمراجعة فقط، ولم يُطبّق على Supabase.  
**فرع العمل:** `feature/job-alerts-system`

## قرارات المنتج
- تنبيهات فورية ويومية اختيارية؛ لا تُفعّل تلقائياً، ويختار المستخدم تفعيلها ثم يحدد الفوري أو اليومي أو كليهما.
- القنوات اختيارية: صندوق إشعارات وظيفتي وWeb Push على الهاتف.
- الخدمة الأساسية مجانية، مع قابلية إضافة Premium مستقبلاً دون تعطيل التنبيهات الأساسية.
- لا نطلب إذن Push عند فتح الصفحة؛ نطلبه بعد اختيار المستخدم تفعيل إشعارات الهاتف.
- إيقاف تنبيهات الوظائف لا يلغي اشتراك Push العام؛ لأن الاشتراك الحالي قد يخدم إشعارات حالة طلبات التقديم أيضاً.

## نتائج تدقيق البنية الحالية
- جدول `jobs` يستخدم `status='published'` للنشر و`pending` للمراجعة، مع `closed` و`rejected`.
- أنواع العمل المعرفة في نموذج نشر الوظائف: `full_time`, `part_time`, `remote`, `contract`, `temporary`, `internship`.
- يوجد حقل `jobs.state` للولاية، ولا يوجد حتى الآن قاموس موحد للمدن؛ لذلك نطاق V1 يدعم الولايات فقط، وتؤجل المدن إلى أن يتم توحيدها.
- توجد جداول التصنيفات والتخصصات، مع FK مركب يضمن انتماء التخصص للتصنيف.
- يوجد `push_subscriptions` وآلية Web Push حالية وService Worker `/sw.js`، إضافة إلى Edge Function `send-application-status-push`.
- اشتراك Push الحالي يخدم إشعارات حالة الطلبات؛ ستضاف تفضيلات مستقلة لتحديد ما إذا كان المستخدم يريد Push لتنبيهات الوظائف.
- جدول `in_app_notifications` يتطلب `application_id` ويرتبط بطلب تقديم؛ لذلك لن نستخدمه لتنبيهات الوظائف.
- امتدادا `pg_cron` و`pg_net` غير مثبتين حالياً، لكنهما متاحان ضمن الامتدادات الممكنة. لم يتم تفعيلهما. يجب اختيار المجدول واعتماده قبل إنشاء أي مهمة دورية.

## قواعد المطابقة
1. الوظيفة لا تدخل نظام التنبيه إلا عند تحولها إلى `published`. يشمل ذلك الوظيفة التي تنشر مباشرة عند الإدراج بسبب آلية النشر الحالية، والوظيفة التي تنتقل من `pending` إلى `published` بعد مراجعة الإدارة.
2. لا تُرسل تنبيهات للوظائف المعلقة أو المرفوضة أو المغلقة.
3. اختيار تصنيف رئيسي دون تخصصات يعني مطابقة جميع تخصصات ذلك التصنيف.
4. اختيار تخصص فرعي يعني مطابقة التخصص المختار، مع احترام التصنيف الأب.
5. عدم اختيار موقع أو نوع عمل يعني عدم تقييد المطابقة بذلك الشرط.
6. قيد التفرد على المستخدم والوظيفة يمنع إنشاء تنبيه مكرر.
7. لا تعاد الوظيفة في ملخص يومي لاحق بعد تسجيل تسليمها لذلك المستخدم.

## سلوك القنوات والتوقيت
- **فوري:** يُنشأ تنبيه لكل وظيفة مطابقة، ثم يُرسل عبر القنوات التي اختارها المستخدم.
- **يومي:** تجمع الوظائف المطابقة الجديدة وتُرسل في ملخص واحد في الوقت والمنطقة الزمنية المحفوظين. لا يرسل ملخص فارغ.
- **كلاهما:** يرسل التنبيه الفوري، ثم يدرج الوظيفة مرة واحدة في ملخص اليوم كتذكير/تجميع يومي؛ هذا التكرار مقصود لأن المستخدم اختار القناتين الزمنيتين.
- إشعارات الموقع هي صندوق التنبيهات وسجلها الأساسي؛ Push قناة إضافية قد تتأثر بإذن المتصفح أو اتصال الجهاز.
- يدعم سجل التسليم قناة `daily_digest` ومعرّف دفعة مشتركاً لتجميع عناصر الملخص الواحد.

## بنية البيانات المقترحة
- `job_alert_preferences`: إعدادات المستخدم وتوقيت الملخص ومنطق القنوات.
- `job_alert_preference_categories`: التصنيفات المختارة.
- `job_alert_preference_specialties`: التخصصات المختارة.
- `job_alert_preference_locations`: الولايات المختارة.
- `job_alert_preference_employment_types`: أنواع العمل المختارة.
- `job_alert_notifications`: سجل إشعارات الوظائف مستقل عن إشعارات الطلبات.
- `job_alert_deliveries`: حالة كل محاولة تسليم، وإعادة المحاولة، وتجميع الملخص.
- `job_alert_outbox`: طابور موثوق للأحداث التي تنتج عند نشر وظيفة.

## الأمن
- RLS على جميع الجداول.
- كل مستخدم يرى ويدير تفضيلاته واختياراته فقط.
- المستخدم يقرأ إشعاراته ويعدل علامة القراءة فقط.
- الطابور وسجل محاولات التسليم يديرهما العامل الموثوق فقط.
- لا تظهر مفاتيح الخدمة في المتصفح.
- العامل يتحقق من حالة الوظيفة المنشورة ومن إعدادات المستخدم قبل التسليم.
- استخدام قيد فريد لمنع التكرار، وقفل/حجز مهام الطابور لمنع المعالجة المتزامنة.
- إعادة المحاولة للأخطاء المؤقتة مع تأخير تصاعدي وحد أقصى للمحاولات.

## الدفع المستقبلي
لا تنشأ بوابة دفع أو جداول اشتراكات الآن. تبقى المطابقة الأساسية مستقلة عن أي خطة، ويمكن إضافة طبقة استحقاقات منفصلة لاحقاً. لا نضع حدوداً مدفوعة حالياً على إشعارات الفرص الأساسية.

## خطة التنفيذ
1. مراجعة مسودة SQL والسياسات والقيود.
2. اختيار آلية جدولة بعد فحص إعدادات Supabase واعتمادها.
3. موافقة منفصلة على تطبيق SQL في بيئة اختبارية.
4. بناء واجهة التفضيلات.
5. بناء عامل المطابقة والتسليم الفوري والملخص اليومي.
6. ربط Push دون التأثير على إشعارات حالة الطلبات الحالية.
7. معاينة Vercel واختبارات حسابين أو أكثر.
8. مراجعة أمنية وأدائية، ثم موافقة مستقلة قبل الإنتاج.

## حدود العمل المنجز حتى الآن
- تم إنشاء فرع `feature/job-alerts-system`.
- أضيفت هذه الوثيقة ومسودة SQL إلى الفرع.
- لم تُنشأ جداول أو سياسات أو triggers في Supabase.
- لم تُفعّل امتدادات أو مهام مجدولة.
- لم يُعدّل `index.html` أو `sw.js`.
- لم تُنشر Edge Function جديدة ولم تُرسل تنبيهات.
- لم يحدث نشر إلى Production.
