## Execution rules

- Keep changes isolated in feature branches and reviewed pull requests.
- Preserve production data and the recovered migration archive. Never replay archived SQL.
- Prefer the existing free GitHub Actions PostgreSQL 17 validation path; do not create paid database branches or require a credit card.
- Do not run production DDL, change production authorization, enable payment collection, or incur charges without a separately reviewed release decision.
- Test authorization at the database/API layer; hiding a button is not access control.
- Maintain Arabic/English support, RTL/LTR behavior, and mobile usability.
- Record actual test evidence. Mark a task complete only after its acceptance criteria pass.

## Baseline findings (read-only review)

1. The production Vercel deployment is **READY** and its Git metadata matches the current `main` commit above.
2. The production Supabase project is active and reports 27 applied migrations; latest is `20261110173838 v1_15_security_performance_hygiene`.
3. The existing admin UI in `index.html` currently centers on company approval and pending-job review. It is not yet a full operations console.
4. The admin button is hidden unless `is_admin()` returns true, and `openAdminDashboard()` also checks the cached admin state. This frontend gating is not sufficient by itself; each privileged database operation must be protected by RLS/RPC authorization.
5. Supabase reports four authenticated-callable SECURITY DEFINER functions: `is_admin`, `finalize_job_hiring`, `update_individual_job_application_status`, and `update_owned_company_description`. Their definitions were inspected read-only and use an empty search_path. Their per-role behavior still requires dedicated adversarial tests before altering grants or execution mode.
6. The `admin_users` and `push_notification_events` tables have RLS enabled and no policies. Preserve their closed posture unless a reviewed design proves a policy is required.
7. Multiple permissive policies on jobs, companies, applications, profiles, resumes and taxonomy tables represent different actor paths. Do not combine them blindly.
8. Supabase Performance Advisor reports one duplicate index pair on `applications`: `applications_job_id_candidate_id_key` and `applications_one_per_candidate_job`. Preserve the UNIQUE constraint while evaluating a safe cleanup migration.
9. Security Advisor also reports `pg_net` in `public` and leaked-password protection disabled. Investigate dependencies and current plan capabilities before proposing changes.
10. No active GitHub Issues existed at the start of this roadmap. Issues #30–#34 now serve as the task tracker. No dedicated project-task markdown file existed at the expected `docs/PROJECT_TASKS.md` path.

## Delivery sequence

### Phase 0 — database and authorization guardrails
Complete DB-01 first. Add focused tests for administrator/non-administrator, company owner/non-owner, individual poster, candidate, and anonymous access. Keep existing production behavior unchanged until tests establish a safe migration path.

### Phase 1 — administration
Map the current admin screens and all privileged calls. Design the admin information architecture before adding features. Introduce an audit-log schema only after deciding which actions are sensitive, how long logs are retained, and how to prevent tampering. Admin management of users must not expose secrets, authentication credentials, or private CVs beyond legitimate review needs.

### Phase 2 — external advertising
Separate advertiser identity verification from ad approval. Model source status and ad status independently. Public rendering must require an approved source, approved ad, active date range, and non-suspended state. Treat external links and uploaded creative as untrusted input.

### Phase 3 — commercial plans
Research pricing and local market feasibility before setting prices. Implement plan definitions and entitlements as configurable data. Trial/test subscriptions must not imply a real payment or automatically renew. Enforce quotas in trusted server/database logic, not only client-side UI.

### Phase 4 — release acceptance
Run migration smoke tests and focused RLS tests on the free PostgreSQL 17 CI path, then preview functional tests, mobile and bilingual checks, and finally a reviewed production rollout. Keep a rollback plan for both app and schema changes.

## Explicit non-goals until separately approved

- No real payment collection or payment gateway integration.
- No paid Supabase/Vercel add-ons, paid test environments, or card requirement.
- No automatic publication of external advertisements.
- No broad grants or policies on `admin_users`.
- No destructive schema cleanup based solely on advisor warnings.
- No production migration or deployment based only on a green local/CI test.
