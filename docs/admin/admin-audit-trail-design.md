# V1.16 — Administrative audit trail design

**Status:** Design proposal only; not implemented.  
**Reviewed against:** production schema and `index.html` on 2026-11-10.  
**Scope:** Administrative actions in the Wazifti operations console.

## 1. Why this is required

The production schema currently has no `audit_logs` or `admin_audit_logs` table. The admin console can review applications, companies and jobs, but sensitive write actions should not be added until the system can record who performed an action, what changed, when it happened, and whether the business mutation succeeded.

This proposal does not create a table, migration, policy, function, or production change.

## 2. Initial event model

Proposed table: `public.admin_audit_logs`.

| Column | Type | Purpose |
|---|---|---|
| `id` | uuid primary key | Event identifier; generated by the database |
| `actor_user_id` | uuid, not null | Authenticated actor (`auth.uid()`), FK to `auth.users(id)` |
| `action` | text, not null | Stable action key, e.g. `job.approve`, `job.reject`, `company.verify`, `application.status_change` |
| `entity_type` | text, not null | Allowlisted resource type: `job`, `company`, `application`, later `advertisement` |
| `entity_id` | uuid, not null | Identifier of the affected resource |
| `before_data` | jsonb, nullable | Allowlisted prior values only |
| `after_data` | jsonb, nullable | Allowlisted resulting values only |
| `reason` | text, nullable | Short moderation reason where required; length-limited |
| `request_id` | uuid, nullable | Correlation ID shared by related events in one operation |
| `created_at` | timestamptz, not null | Database-generated UTC timestamp |

Do not store CVs, resume/storage URLs, cover letters, phone numbers, passwords, access tokens, full profile records, or arbitrary request bodies in audit events. Do not record IP addresses or device fingerprints in the first release. Before/after JSON must be constructed server-side from explicit allowlists, not accepted verbatim from the browser.

## 3. Write and read security

1. Enable RLS on the audit table.
2. No direct INSERT, UPDATE, or DELETE grants/policies for `anon` or ordinary `authenticated` clients.
3. Admin read access, if needed, must use a narrowly scoped SELECT policy based on the existing `is_admin()` check. Do not open the table to public users.
4. Writes must occur only inside trusted database functions that:
   - derive actor identity from `auth.uid()`, never from a client-supplied actor ID;
   - verify the actor is an administrator using the established admin authorization mechanism;
   - validate action/entity allowlists and permitted state transitions;
   - perform the business mutation and insert the audit event in the same transaction;
   - raise an error and roll back the mutation if the audit insert fails.
5. Revoke PUBLIC/anon execution on privileged functions and grant only the minimum required authenticated execution. Verify function ownership, SECURITY DEFINER behavior, empty/secure `search_path`, and role behavior with adversarial tests.
6. Treat the log as append-only at the application/database privilege layer. No UI action may edit or delete an event. A future correction should be a new compensating event, not mutation of history.

## 4. Actions to audit first

Initial proposed allowlist:
- `company.verify`, `company.reject`
- `job.approve`, `job.reject`, `job.pause` (only if pause is a supported state)
- `application.status_change` (only after the valid transition graph is verified)
- `advertiser.verify`, `advertisement.approve`, `advertisement.reject` in V1.17, after those entities exist.

Do not add user deletion, account suspension, role changes, or arbitrary profile edits in this phase. These require separate lifecycle and recovery designs.

## 5. Application status caveat

The employer UI currently exposes `submitted`, `reviewing`, `shortlisted`, `rejected`, and `accepted`. The accepted path invokes `finalize_job_hiring`; other paths differ for individual posters and company employers. Historical production rows have also shown statuses not present in the current employer selector.

Therefore:
- This list is an observed UI set, not a complete database enum or an approved transition matrix.
- Do not infer that every status can transition to every other status.
- Before enabling admin application moderation, inspect the full RPC definitions, constraints, triggers, and real status distribution; then define and test an explicit transition graph.
- The current admin applications panel remains read-only.

## 6. Retention, access, and operations

- Decide a retention period with the project owner before implementation; do not silently purge audit history.
- Restrict audit-log access to administrators with a legitimate operational need.
- Paginate and filter by date, action, actor, and entity; avoid bulk export in the first release.
- Consider immutable backup/export separately before any retention cleanup.
- Audit events are operational records, not a substitute for user-facing notifications or legal compliance review.

## 7. Migration and rollout plan

1. Confirm the action allowlist, retention period, reason requirements, and whether admins need a read-only audit viewer.
2. Add a new migration using the Supabase CLI workflow; do not hand-create a migration filename or run DDL directly in production.
3. Extend free PostgreSQL 17 CI tests for table shape, RLS, grants, function execution, append-only behavior, and atomic rollback when audit insertion fails.
4. Test administrator positive paths and non-admin/anonymous negative paths, including spoofed actor IDs, entity IDs, and malformed before/after payloads.
5. Deploy schema and RPCs only after reviewed migration checks and a rollback plan.
6. Add one low-risk audited admin action first; verify the audit row and business result in the same transaction.
7. Only then add further moderation controls and a read-only audit viewer.

## 8. Acceptance criteria

- Every privileged admin mutation creates exactly one corresponding audit event.
- Failed mutations create no success event; failed audit writes prevent the business mutation.
- Actor identity cannot be spoofed by the client.
- Ordinary users and anonymous clients cannot read or write audit rows.
- Audit rows cannot be updated or deleted through client APIs.
- No CV, cover-letter, phone, credential, or storage URL data appears in logs.
- Arabic/English and mobile acceptance pass for any future audit viewer.
- No production schema change is made until the migration and security tests pass.

## 9. Current implementation state

- PR #38 adds a read-only, paginated, bilingual application overview; it does not write application statuses.
- Existing admin access policies on applications, companies, and jobs were reviewed; no RLS expansion is proposed here.
- No audit table exists in the reviewed production public schema.
- No database changes are part of this document.
